# Живые сессии с тренером на портале (интеграция с SABAK.kz)

> План от 2026-08-21, решения владельца внесены (§9). Связано: docs/B2B-PLAN.md, docs/PRICING-PLAN.md,
> калькулятор пакета «Платформа + живой тренер» (`src/components/landing/seats-calculator.tsx`).

## 1. Задача

Пакет с тренером уже продаётся: к корпоративному доступу добавляются вводная
онлайн-сессия (1 ч), итоговая онлайн-сессия (1 ч) и группа сопровождения в
мессенджере — 3 × 100 $ фиксированно на компанию (`lib/pricing` `TRAINER_PACK`).
Сейчас это обещание в счёте, но не функция платформы: назначить встречу, собрать
на неё отдел и отдать запись пока негде.

Цель: тренер планирует и проводит встречу **не выходя из study.activesales**, а
работник компании входит в неё из своего кабинета одной кнопкой — не заводя
аккаунт где-то ещё и не раскрывая своё имя (правило 9: платформа не получает ПДн
работников).

Видеоинфраструктуру не строим — берём соседний продукт SABAK.kz.

## 2. Что уже умеет SABAK (проверено по коду, не по обещаниям)

`/Users/nurlan/Documents/projects/sabak.kz`, NestJS + LiveKit SFU + Egress +
MinIO + ClickHouse.

| Возможность | Где в коде | Что это даёт нам |
|---|---|---|
| Workspace в режиме `BUSINESS` | `School.mode` (`WorkspaceMode`) | Организация-клиент = отдельный tenant, не «школа» |
| Собственные встречи вне расписания | `POST /my/lessons`, `POST /my/lessons/instant` | Тренер создаёт сессию программно |
| Серии повторяющихся встреч | `LessonSeries` | Регулярные разборы, если продадим их позже |
| Гостевой вход без регистрации | `POST /m/:lessonId/join` → JWT | Работник входит по ссылке, без учётки SABAK |
| Настройка анкеты гостя | `guestRequireFullName/Position/Contact` (по умолчанию всё `false`) | Вход по обезличенному логину — ПДн не собираются |
| Режим вебинара | `Lesson.kind = WEBINAR`, `promote`/`demote` | Вводная лекция на 30 человек без хаоса |
| Q&A и чат | `WebinarQuestion`, `ChatMessage` | Итоговая сессия «ответы на вопросы» |
| Запись + расшифровка | `Recording`, `Transcript`, LiveKit Egress | Отдаём запись тем, кто не смог |
| Ссылки на записи с аудиторией и сроком | `RecordingShare` (`WORKSPACE/PARTICIPANTS/PUBLIC`), `RecordingShareAccess` | Раздача записи без выгрузки файла к нам |
| Посещаемость по вебхукам LiveKit | `Attendance`, `POST /webhooks/livekit` | Отчёт «кто был» в кабинет компании |
| Брендирование лобби | `School.brandLogoUrl`, `brandColor` | Гость видит ACTIVE SALES, а не чужой сервис |
| E2EE-режим | `Lesson.e2eeEnabled` (запись при этом отключается) | Запасной вариант для параноидального клиента |

Чего в SABAK нет и что придётся учесть:

- **Нет машинной авторизации** (ни API-ключей, ни `client_credentials`): все
  операции идут от JWT пользователя.
- **Встраивание в iframe закрыто**: `frame-ancestors 'none'` и
  `X-Frame-Options: SAMEORIGIN` (`apps/frontend/src/proxy.ts`).
- Часть операций закрыта фиче-флагами биллинга (`RequireFeature(FEATURES.CREATE_LESSON)`),
  то есть нужен подходящий тариф/entitlement для нашего аккаунта.

## 3. Как это делают другие

- **Kajabi** — единственный из «курсовых» платформ с нативными live-сессиями
  внутри курса: расписание, напоминания, запись падает в тот же урок. Это ровно
  наш целевой сценарий.
- **Teachable / Thinkific** — live только через подключение своего аккаунта Zoom:
  платформа хранит ссылку и время, а сама встреча живёт снаружи. Дёшево в
  реализации, но ученик уходит из кабинета, а запись возвращается руками.
- **Moodle + BigBlueButton** — серверная интеграция по API: LMS создаёт комнату,
  раздаёт роли, забирает запись. Ближайший аналог тому, что мы делаем с SABAK.
- **LTI 1.3 + LTI Advantage** (Deep Linking, Names and Roles, Grade Services) —
  индустриальный стандарт, когда LMS и видеосервис принадлежат **разным**
  компаниям. У нас обе стороны свои, поэтому платить сложностью LTI не за что:
  берём прямой API, а из LTI заимствуем идею — единый вход и возврат результата
  (посещаемость, запись) в карточку курса.

Вывод: делаем «как Kajabi» по опыту пользователя, «как Moodle+BBB» по технике.

## 4. Архитектура: три варианта и выбор

| Вариант | Суть | Плюсы | Минусы |
|---|---|---|---|
| **A. Ссылка** | Кнопка в кабинете открывает `https://sabak.kz/m/<lessonId>` в новой вкладке | Дни работы, ноль рисков | Уход с портала, второй бренд в лобби (смягчается брендированием workspace) |
| **B. iframe** | Гостевая страница SABAK внутри нашей страницы | Внешне «на портале» | Требует правки CSP в SABAK, двойная авторизация, ломкие камеры/микрофон в iframe |
| **C. Своя комната** | study.activesales получает LiveKit-токен через SABAK и рендерит комнату сам (`@livekit/components-react`) | Полностью наш UI и бренд, вход одним кликом из кабинета | Свой UI видео (сетка, экран, чат), дубль части функций SABAK |

**План: A → C.** Вариант A — MVP на первые продажи пакета (он уже в прайсе), C —
целевое состояние. B отбрасываем: CSP-запрет в SABAK стоит примерно столько же,
сколько путь C, а результат хуже.

Ключ к C: гостевой `POST /m/:id/join` уже возвращает JWT, а `POST /lessons/:id/join`
по нему выдаёт `livekitToken` + `livekitUrl`. То есть нам не нужен доступ к
внутренностям SABAK — только два вызова и SFU.

## 5. Что появится в study.activesales

### 5.1 Данные (Prisma)

```prisma
model LiveSession {
  id            String   @id @default(cuid())
  orgId         String            // организация-клиент (B2B-контур)
  licenseId     String?           // к какой лицензии относится пакет
  kind          LiveSessionKind   // INTRO | FINAL | EXTRA
  title         String
  scheduledAt   DateTime          // хранится в UTC
  timezone      String            // IANA-зона клиента: Europe/Minsk, Asia/Almaty…
  durationMin   Int      @default(60)
  status        LiveSessionStatus // PLANNED | LIVE | FINISHED | CANCELLED
  sabakLessonId String?  @unique  // id урока на стороне SABAK
  joinUrl       String?           // гостевая ссылка (вариант A)
  // Постоянной ссылки на запись НЕ храним (см. §6 п. 3) — только признак того,
  // что запись готова, и её id в SABAK; ссылка выдаётся на час по клику.
  recordingId   String?
  recordingReady Boolean @default(false)
  attendedCount Int?              // сколько человек было, без имён
}
```

Группу сопровождения в модели не храним вовсе: тренер создаёт её сам под каждую
компанию (в Беларуси — Viber) и сам приглашает участников. Платформа в этот
контур не лезет — ни ссылки, ни списка участников, ни модерации. Меньше кода и
ни одного лишнего персонального данного.

Посещаемость хранится как факт, а не как хронометраж: у каждой сессии —
`LiveSessionAttendance { sessionId, memberLogin, attended Boolean }`, где
`memberLogin` — обезличенный `<slug>-0042`. Порог: участник считается
присутствовавшим, если пробыл в комнате ≥ 10 минут (минуты приходят из SABAK,
но наружу не показываются — в отчёте компании только «был / не был»).

Персональных данных здесь не появляется ни в одном поле: ни ФИО, ни контактов,
ни длительности участия.

### 5.2 Интеграционный слой `src/lib/live/sabak.ts`

- логин сервисного аккаунта тренера (`SABAK_BASE_URL`, `SABAK_SERVICE_LOGIN`,
  `SABAK_SERVICE_PASSWORD`), кеш access/refresh-токена;
- `createSession()` → `POST /my/lessons` (kind `WEBINAR` для вводной,
  `MEETING` для итоговой, `allowGuests: true`, анкета гостя выключена);
- `guestToken(login)` → `POST /m/:id/join` с `displayName = <slug>-0042`;
- `roomToken()` → `POST /lessons/:id/join` (для варианта C);
- `recordingLink()` → `GET /lessons/:id/recordings` + `RecordingShare` с
  `expiresAt` ≈ 1 час и `allowDownload: false`, **создаётся в момент клика**
  сотрудника, а не заранее (см. §6 п. 3);
- посещаемость: `GET /lessons/:id/attendance` после `FINISHED` → сворачиваем в
  «был / не был» по порогу 10 минут и сохраняем только это.

Все вызовы — через Job-очередь с ретраями и идемпотентностью (правило 8):
падение SABAK не должно ронять страницу кабинета. Если сессию создать не удалось,
владелец видит статус «не создана» и кнопку «повторить», а не молчаливую пустоту.

### 5.3 Экраны

- **`/admin/live`** (владелец/тренер): список сессий, форма планирования
  (организация → тип → дата/время в зоне клиента → длительность), кнопки
  «Начать», «Скопировать ссылку», «Отменить», после встречи — «Отправить запись».
- **`/org/[orgId]`** (кабинет компании): блок «Встречи с тренером» — ближайшая
  сессия, кнопка входа за 15 минут до старта, прошедшие с записями, `.ics` для
  календаря.
- **Кабинет ученика-работника**: баннер на дашборде в день встречи и запись
  после — в том же курсе, где идёт обучение.
- **Лендинг `/business`**: у выбранного пакета с тренером — та же цепочка
  словами, чтобы обещание в калькуляторе и функция в кабинете совпадали.

### 5.4 Напоминания

Свои, не SABAK-овские (у нас нет e-mail работников): карточка в кабинете,
Telegram владельцу и в группу сопровождения, `.ics`-вложение при выдаче доступа.
`LessonReminder` на стороне SABAK не используем.

## 6. Приватность (Закон РБ № 99-З, правило 9)

1. Работник входит гостем под обезличенным логином; `guestRequireFullName`,
   `guestRequirePosition`, `guestRequireContact` — всегда `false`.
2. Камера у аудитории по умолчанию выключена (`WEBINAR` этого и требует):
   изображение и голос — биометрия по смыслу, и собирать их «по умолчанию» нельзя.
   Кто включает камеру — делает это осознанно, с предупреждением в лобби.
3. Запись ведётся только при явном уведомлении в лобби; хранится в контуре SABAK
   (`recordingRetentionDays` на workspace) и доступна **только компании, для
   которой прошла встреча** (решение владельца). Технически: постоянных ссылок
   не существует — кабинет проверяет членство в организации через `lib/access`
   и запрашивает у SABAK одноразовую ссылку на час, без скачивания. Так утечка
   пересланного URL живёт час, а не вечно. Как материал курса записи не
   переиспользуются.
4. Оферту `/offer-b2b` дополняем разделом о живых сессиях: кто оператор, что
   записывается, сколько хранится, как отозвать.
5. Для клиента, которому запись неприемлема, — режим `e2eeEnabled` (SFU видит
   только шифрованный поток, записи нет вовсе).

## 8. Риски

| Риск | Что делаем |
|---|---|
| Нет S2S-авторизации в SABAK | Э1 живёт на сервисном аккаунте; параллельно предлагаем в SABAK `client_credentials` + scoped-ключи — это правильная развязка двух продуктов |
| SABAK недоступен в момент встречи | Ссылка сохранена заранее в `LiveSession.joinUrl`; кабинет показывает её из своей БД, не дёргая API |
| Четыре часовых пояса (Минск/Москва +3, Астана/Ташкент +5) | Храним UTC + IANA-зону клиента, показываем обе зоны в карточке и в `.ics` |
| Тариф SABAK ограничивает создание встреч | Уточнить `FEATURES` и лимиты до Э1 — иначе упрёмся в 403 на первом же клиенте |
| Срок хранения записей | Ставим `recordingRetentionDays` явно и пишем этот срок в оферту, чтобы не обещать «навсегда» |
| Дубль UI на Э3 | Берём только необходимое (видео, экран, чат, рука); доска, опросы и Q&A остаются в SABAK |

## 10. Состояние на стороне SABAK

API у SABAK есть — REST `/api/v1` на JWT, и функционально в нём уже лежит всё
нужное (§2). Нет только программного входа: любая операция требует токена живого
пользователя. Требования к сервисному доступу вынесены в отдельное задание для
команды SABAK — `docs/SABAK-INTEGRATION-REQUEST.md`: API-ключи
(`client_credentials`) со скоупами, идемпотентное создание встречи, выдача
гостевого доступа по обезличенному `externalId`, посещаемость сводкой, ссылка на
запись по требованию и вебхуки к нам.

Брендирование workspace берём с самой платформы: логотип
`https://study.activesales.by/logo.png`, акцентный цвет `#f4003a`.

До появления ключей интеграция может жить на учётке тренера (логин и пароль в
секретах сервера) — это работоспособный, но временный вариант, и в задании для
SABAK он назван как то, что нужно заменить.

### Как включить

Сервисный доступ на стороне SABAK готов (их `docs/S2S_API.md`): ключи
`client_credentials` со скоупами `lessons:write`, `lessons:read`,
`guests:issue`, `recordings:read`, идемпотентное создание встречи, гостевой
доступ по `externalId` с одноразовым билетом на 15 минут, сводка посещаемости и
четыре исходящих вебхука с HMAC-подписью. Пароль учётки тренера нам больше не
нужен — этот режим из кода убран.

**URL для вебхуков, который надо указать при создании ключа:**
`https://study.activesales.by/api/webhooks/sabak`

1. В секреты сервера: `LIVE_SESSIONS_ENABLED=true`, `SABAK_BASE_URL`,
   `SABAK_CLIENT_ID`, `SABAK_CLIENT_SECRET`, `SABAK_WEBHOOK_SECRET`.
2. Открыть `/admin/live` — вверху страницы видно состояние связи и от чьего имени
   мы работаем. Пока флага нет, встречи всё равно планируются: они сохраняются у
   нас и создаются в SABAK кнопкой «Повторить», как только связь появится.
3. Проверить сквозной сценарий: назначить встречу → ссылка в кабинете компании →
   вход работника → после встречи статусы, запись и «был / не был» приезжают
   вебхуками сами (кнопка «Итоги» — если событие потерялось).
4. Записать себе `recordingRetentionDays` из `/admin/recordings` SABAK — это
   срок хранения записей, его надо назвать в оферте для организаций.

Ошибки SABAK переведены в человеческие фразы: `402 ENTITLEMENT_REQUIRED`
показывается как «учётке тренера не выдан тариф на встречи», а не кодом —
искать причину надо в админке SABAK, а не в нашем коде.
