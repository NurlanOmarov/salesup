## 1. Что делаем

Продаём доступ **организации**, а не человеку. Организация получает свой кабинет, в котором:

- видит купленные лицензии (курс × количество мест × срок);
- заводит сотрудников (или раздаёт им коды самообслуживания);
- видит прогресс каждого сотрудника и сводку по отделам;
- выгружает отчёт (CSV) для HR;
- отзывает доступ у уволившегося и передаёт место другому.

Владелец платформы (OWNER) при этом остаётся «автопилотом»: создал организацию, выдал лицензии — дальше клиент обслуживает себя сам. Ручных операций у владельца не прибавляется.

### Ключевое архитектурное решение

**Не трогаем `Enrollment` как источник доступа.** Организация и лицензии — это слой *выдачи*, который порождает те же самые `Enrollment` (с `source = B2B` и ссылкой на лицензию). `lib/access.ts` не узнаёт о существовании организаций вообще — правило 1 остаётся в силе, e2e-тесты доступа не переписываются.

Следствие: «отозвать доступ у сотрудника», «лицензия истекла», «организацию заморозили» — всё это операции, которые проставляют `Enrollment.revokedAt` / `expiresAt`. Никакой второй ветки проверки доступа не появляется.

## 2. Модель данных

Дополнения к `prisma/schema.prisma`:

```prisma
enum OrgStatus {
  ACTIVE
  SUSPENDED   // не оплачено / заморожена — доступы отзываются джобом
  ARCHIVED
}

enum OrgRole {
  ORG_ADMIN    // кабинет компании: сотрудники, лицензии, отчёты
  ORG_LEARNER  // обычный сотрудник-ученик
}

/// Клиент-организация. Реквизиты юрлица персональными данными не являются —
/// ПДн-риск сосредоточен только в contactEmail (один человек, по договору).
model Organization {
  id           String    @id @default(cuid())
  slug         String    @unique  // короткий код: acme → логины вида acme-0042
  name         String              // юрлицо/бренд
  contactEmail String?             // e-mail ответственного (единственная ПДн-точка, см. §5)
  contactNote  String?             // произвольный контакт (Telegram/телефон) — опционально
  status       OrgStatus @default(ACTIVE)
  /// Счётчик для генерации логинов acme-0001, acme-0002… (инкремент в транзакции)
  loginSeq     Int       @default(0)
  createdAt    DateTime  @default(now())
  updatedAt    DateTime  @updatedAt

  memberships OrgMembership[]
  licenses    OrgLicense[]
  groups      OrgGroup[]
  invites     OrgInvite[]
  keyWraps    OrgKeyWrap[]
}

/// L2-криптография (§5.2). Случайный AES-256 ключ организации хранится ТОЛЬКО в
/// обёрнутом виде: по одной записи на каждого org-админа + одна на recovery-код.
/// Сервер никогда не видит ни ключ, ни парольную фразу — только blob и параметры KDF.
model OrgKeyWrap {
  id         String   @id @default(cuid())
  orgId      String
  /// Владелец обёртки: userId org-админа, либо null для recovery-обёртки
  userId     String?
  kind       String   // 'admin' | 'recovery'
  wrappedKey String   // base64: AES-GCM(orgKey) под ключом из парольной фразы
  kdfSalt    String   // base64
  kdfParams  Json     // { alg: 'PBKDF2-SHA256', iterations: 600000 } — версионируется
  createdAt  DateTime @default(now())

  org  Organization @relation(fields: [orgId], references: [id], onDelete: Cascade)
  user User?        @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@unique([orgId, userId, kind])
}

/// Отдел/филиал/поток — метка для группировки отчётов. Не ПДн.
model OrgGroup {
  id     String @id @default(cuid())
  orgId  String
  name   String
  org    Organization @relation(fields: [orgId], references: [id], onDelete: Cascade)
  memberships OrgMembership[]

  @@unique([orgId, name])
}

/// Членство пользователя в организации. Здесь же — псевдоним сотрудника.
/// Открытым текстом хранится ТОЛЬКО платформенный код (User.login = acme-0042).
/// Кто за ним стоит — знает клиент; на платформе это лежит лишь в labelEnc (L2).
model OrgMembership {
  id       String   @id @default(cuid())
  orgId    String
  userId   String
  role     OrgRole  @default(ORG_LEARNER)
  groupId  String?
  /// Метка сотрудника (ФИО, табельный номер — что решит клиент), зашифрованная
  /// в браузере ключом организации. Сервер хранит непрозрачный blob. См. §5.2.
  labelEnc String?
  isActive Boolean  @default(true)
  joinedAt DateTime @default(now())
  deactivatedAt DateTime?

  org   Organization @relation(fields: [orgId], references: [id], onDelete: Cascade)
  user  User         @relation(fields: [userId], references: [id], onDelete: Cascade)
  group OrgGroup?    @relation(fields: [groupId], references: [id], onDelete: SetNull)

  @@unique([orgId, userId])
  @@index([orgId, isActive])
}

/// Лицензия = ОДИН курс × N мест × срок (решение: единица лицензии — курс×человек).
/// Пул, из которого создаются Enrollment. Сотрудник, которому открыли 3 курса,
/// занимает по одному месту в трёх разных лицензиях. Пакет курсов на будущее
/// делается не новой сущностью, а групповой выдачей нескольких лицензий разом.
model OrgLicense {
  id             String         @id @default(cuid())
  orgId          String
  courseId       String
  seatsTotal     Int
  accessDuration AccessDuration @default(MONTHS_12)
  startsAt       DateTime       @default(now())
  expiresAt      DateTime?      // общий дедлайн лицензии (перебивает срок места)
  note           String?
  createdAt      DateTime       @default(now())

  org         Organization @relation(fields: [orgId], references: [id], onDelete: Cascade)
  course      Course       @relation(fields: [courseId], references: [id], onDelete: Cascade)
  enrollments Enrollment[]

  @@unique([orgId, courseId])
}

/// Код самозаписи: сотрудник вводит его и создаёт себе анонимную учётку (§5.1).
model OrgInvite {
  id         String   @id @default(cuid())
  orgId      String
  code       String   @unique          // 8 символов, без похожих букв
  groupId    String?
  licenseIds Json                       // какие лицензии выдать при активации
  maxUses    Int      @default(1)
  usedCount  Int      @default(0)
  expiresAt  DateTime?
  createdAt  DateTime @default(now())

  org Organization @relation(fields: [orgId], references: [id], onDelete: Cascade)

  @@index([orgId, expiresAt])
}
```

Изменения существующих моделей:

```prisma
enum EnrollmentSource {
  PURCHASE
  MANUAL
  FREE
  B2B        // ← новое: выдан из корпоративной лицензии
}

model Enrollment {
  // ...
  licenseId String?
  license   OrgLicense? @relation(fields: [licenseId], references: [id], onDelete: SetNull)
  @@index([licenseId])
}

model User {
  // ...
  email  String? @unique   // ← становится опциональным (анонимные B2B-учётки без e-mail)
```

> ⚠️ `User.email` из обязательного делается опциональным — это миграция с проверкой всех мест, где `user.email` используется как непустая строка (письма, `Order.email`, дайджест, `/admin/students`). Отдельная задача в фазе 1, не «попутно».

Занятые места считаются запросом `count(Enrollment where licenseId = X and revokedAt is null)` — отдельного счётчика не заводим, чтобы не рассинхронизировать.

## 3. Роли и вход

`User.role` (`STUDENT | OWNER`) **не трогаем**. Роль в организации живёт в `OrgMembership.role`, потому что org-админ обычно ещё и сам учится.

- В сессию Auth.js добавляем `orgId` и `orgRole` (в JWT-callback одним запросом по `OrgMembership`).
- Новый guard `src/lib/auth/guards.ts → requireOrgAdmin()`: есть активное членство с `role = ORG_ADMIN` и `org.status = ACTIVE`, иначе редирект в `/app`.
- `safeAction` получает третий вариант `auth: "orgAdmin"` — и **каждое** действие org-админа дополнительно проверяет, что целевой `membership.orgId === session.orgId`. Это главная точка IDOR-риска в фиче: org-админ не должен уметь дотянуться до чужой организации, подставив id.
- Вход: страница `/login` принимает логин **или** e-mail. Credentials-провайдер ищет по `login` при отсутствии `@`.
- Сброс пароля сотрудника делает org-админ у себя в кабинете (кнопка «сбросить» → временный пароль показывается один раз, `mustChangePassword = true`). Владелец платформы в это не вовлечён — zero-touch сохраняется.

## 4. Экраны

### Кабинет организации — `src/app/(org)/org/*`

| Маршрут | Содержание |
|---|---|
| `/org` | Обзор: занято мест X из Y по каждой лицензии, активность за 7/30 дней, средний прогресс, сколько сотрудников не начинали |
| `/org/employees` | Таблица: код (+расшифрованная метка, если введена фраза), отдел, курсы, % прохождения, последняя активность, статус. Фильтры, поиск, массовые действия |
| `/org/employees/[id]` | Карточка: прогресс по урокам, попытки тестов и баллы, сертификаты (READY/ISSUED), сброс пароля, отзыв доступа, перевод в другой отдел |
| `/org/invites` | Генерация кодов самозаписи (пачкой), печать/выгрузка списка кодов, отзыв неиспользованных |
| `/org/licenses` | Что куплено, сроки, свободные места, кнопка «запросить ещё» (создаёт Lead владельцу) |
| `/org/reports` | Отчёт по курсу/отделу/периоду + экспорт CSV |
| `/org/settings` | Отделы, профиль организации, парольная фраза для меток (L2), контакт ответственного |

### Админка владельца — дополнения к `(owner)/admin`

- `/admin/orgs` — список организаций, создание, выдача лицензий, назначение org-админа, заморозка.
- `/admin/orgs/[id]` — лицензии, места, журнал действий org-админа (в `AdminLog` пишем и его действия с `meta.orgId`).
- В `/admin/analytics` — срез B2B: выручка по организациям (когда появится биллинг), утилизация мест (куплено vs реально учится) — главный аргумент на продление.

### Пошаговый запуск и готовые тексты доступа

Запуск клиента разложен на шаги, которые видны обеим сторонам и закрываются
автоматически по состоянию БД (`src/lib/org/setup.ts`, компонент
`src/components/setup-checklist.tsx`):

- владельцу — в карточке организации `/admin/orgs/[id]`: реквизиты → лицензия →
  ответственный → передача доступа → коды → первые работники. В реестре
  `/admin/orgs` у каждой строки подсказка «дальше: …»;
- ответственному — на «Обзоре» `/org/[orgId]`: лицензии → коды → раздача →
  (по желанию) имена работников.

Шаги общие: коды может создать и ответственный в своём кабинете, и владелец за
него (OWNER допущен в кабинет клиента) — выполненное одним сразу отмечено
у второго.

Тексты выдачи доступа собраны в `src/lib/messages/templates.ts` и показываются
блоком `ShareMessage` (`src/components/share-message.tsx`) везде, где пароль или
код показывается один раз: назначение ответственного и сброс его пароля,
создание ученика и сброс его пароля, создание кодов самозаписи. Копируется
готовое сообщение целиком — с логином, паролем/кодом и инструкцией, что делать
дальше; отправляет его человек сам в мессенджере (писем в MVP нет).

### Кабинет сотрудника — тот же `(student)/app`

**Принципиально: у каждого сотрудника своя учётка и свой вход.** Общих логинов «на отдел» нет — иначе рассыпается всё остальное: прогресс, баллы теста, сертификат, лимиты AI (`AiUsageDay` считает по `userId`), антишаринг (`Device`), геймификация. Это же и защита от «один купил — вся компания посмотрела»: `deviceLimit` работает per-user.

Путь сотрудника:

1. Получает от своего HR код самозаписи (или логин + временный пароль, если org-админ завёл его вручную).
2. `/join` → код → придумывает пароль → сразу попадает в `/app` с уже выданными курсами.
3. Дальше — обычный кабинет ученика без изменений: уроки, тесты, AI-наставник, тренажёры, сертификат.

Отличия для B2B-ученика минимальны и все — косметические: бейдж «обучение от <Организация>» и, если организация включила, — место в рейтинге отдела (по псевдонимам, по умолчанию **выключено**). Никаких отдельных «корпоративных» экранов обучения не делаем: одна кодовая база кабинета для B2C и B2B.

Что при этом сотрудник **не** видит: чужой прогресс, состав лицензий, кабинет `/org`.

## 5. Обезличивание — Беларусь, режим L2

> ⚠️ Ниже — инженерный план, не юридическое заключение. Итоговые формулировки договора, политики и уведомлений должен утвердить юрист по праву РБ. Технические меры описаны так, чтобы юристу было что подтверждать.

### 5.0. Правовая рамка (РБ) и что это меняет в проекте

Применимый закон — **Закон Республики Беларусь от 07.05.2021 № 99-З «О защите персональных данных»**, уполномоченный орган — Национальный центр защиты персональных данных (НЦЗПД). Существенно для нас:

- **Требования локализации базы в РБ в законе нет** — в отличие от РК (№ 94-V) и РФ. Трансграничная передача регулируется отдельно (ст. 9): в страны с надлежащим уровнем защиты — свободно, в прочие — с разрешения НЦЗПД либо по согласию субъекта/для исполнения договора.
- Обезличивание определено как действия, после которых **невозможно без дополнительной информации** определить принадлежность данных субъекту. Именно эту конструкцию мы и строим: дополнительная информация (кто такой `acme-0042`) физически не хранится у нас.
- Обработка ПДн работников нанимателем в рамках трудовых отношений имеет собственное основание — клиенту не придётся собирать согласия ради нашей платформы.

**Следствия для репозитория** (отдельная задача фазы 1, документационная):

1. `CLAUDE.md`, правило 2: убрать «⚠️ Закон РК о ПДн требует хранения базы… целевой — ps.kz / hoster.kz». Текущий VPS (DatabaseMart) остаётся; переезд, если и будет, — по цене/скорости, а не по требованию закона.
2. `CLAUDE.md`, правило 9: переформулировать под РБ — не «минимизация ПДн на временном зарубежном VPS до переезда в РК», а «платформа не обрабатывает ПДн обучающихся; исключения перечислены и ограничены».
3. `docs/MIGRATION.md`: снять статус «приоритетный» с переезда в РК.
4. `docs/DECISIONS.md`: новое решение D-0xx с этой таблицей развилок.

**Честное уточнение.** «Не храним ПДн» верно для **B2B-контура**. Полностью без ПДн платформа не окажется, пока есть: розничные ученики (`User.email`, `name` для сертификата), заявки с лендинга (`Lead.contact`), контакт ответственного от организации. Поэтому базовый комплаенс-минимум остаётся нужен независимо от B2B: политика обработки на сайте, ответственный за внутренний контроль, порядок уведомления НЦЗПД об инциденте, сроки хранения. Обезличивание B2B **радикально сужает** объём и риск, но не отменяет эти три вещи.

### 5.1. Что именно хранится о сотруднике

| Хранится на платформе | Не хранится никогда |
|---|---|
| `login` = `acme-0042` (сгенерирован нами) | ФИО, e-mail, телефон, должность |
| хеш пароля (argon2id) | таблица «код ↔ сотрудник» в открытом виде |
| отдел (`OrgGroup.name`) — организационная единица | адрес, дата рождения, любые кадровые атрибуты |
| прогресс, баллы, попытки, сертификаты | IP и город в открытом виде (§5.3) |
| зашифрованная метка `labelEnc` (ключа у нас нет) | |

Путь без единого ПДн-поля: org-админ генерирует коды (`OrgInvite`) → раздаёт сотрудникам сам, вне платформы → сотрудник на `/join` вводит код и придумывает пароль → создаётся `User` с `login = acme-0042`, `email = null`, `name = null`. Поля `name/phone/email` для B2B-учёток скрыты в UI **и** запрещены в zod-схемах — не «не показываем», а «не принимаем».

Сброс пароля — через org-админа (кнопка в его кабинете), поэтому e-mail сотруднику не нужен даже технически.

Сертификат: механика уже правильная (`Certificate.holderName` не заполняется автоматически, статус `READY`). Для B2B org-админ видит «0042 выполнил условия на 92 %», сам сопоставляет с человеком и запрашивает документ; ФИО вводится один раз в момент выпуска и **не сохраняется** — PDF отдаётся потоком, в `lib/storage` не пишется.

### 5.2. L2 — метки, которые сервер не может прочитать (базовый режим)

Голые коды неудобны, поэтому метка есть — но нечитаемая для нас.

**Схема ключей.** Не выводим ключ шифрования прямо из парольной фразы: иначе смена фразы = перешифровка всех меток, а второй админ невозможен. Вместо этого:

1. При создании организации в браузере генерируется случайный **ключ организации** `orgKey` (AES-256-GCM).
2. Org-админ задаёт парольную фразу → из неё PBKDF2-SHA256 (600k итераций, случайная соль) даёт `KEK`.
3. `orgKey` шифруется под `KEK` и уходит на сервер как `OrgKeyWrap{kind:'admin', userId}`. Сам `orgKey` и фраза на сервер **не уходят никогда**.
4. Дополнительно генерируется **recovery-код** (случайные 32 символа, показывается один раз, «распечатайте и положите в сейф») → вторая обёртка `kind:'recovery'`.
5. Второй org-админ = ещё одна обёртка: действующий админ расшифровывает `orgKey` у себя и оборачивает под фразу нового. Ключ при этом не покидает браузер.

**Работа в кабинете.** При входе org-админ вводит фразу → `orgKey` расшифровывается и живёт в памяти вкладки (`CryptoKey` с `extractable: false`, sessionStorage не используем). Метки расшифровываются при рендере списка. Кабинет без фразы работает — просто вместо меток видны коды; это допустимый режим для «посмотреть общий прогресс».

**Что ломается и как с этим жить:**

| Ограничение | Решение |
|---|---|
| Нет серверного поиска/сортировки по метке | клиентский поиск: список сотрудников грузится и фильтруется в браузере. До ~2000 сотрудников это незаметно; дальше — пагинация по коду + поиск в загруженной странице |
| CSV-экспорт с метками | собирается **в браузере** (расшифровали → сформировали файл → скачали). Серверный экспорт отдаёт только коды |
| Потеря фразы и recovery-кода | метки безвозвратно теряются; прогресс, коды и доступы целы. Предупреждение при настройке — обязательное, с чекбоксом-подтверждением |
| Соблазн сделать «blind index» (HMAC метки) для серверного поиска | **не делаем**: HMAC от ФИО уязвим к перебору по словарю фамилий и убивает весь смысл. Явно фиксируем как запрещённое решение |
| Метка в письмах-сводках | письма org-админу содержат только коды и агрегаты; никаких меток |

Криптографию изолируем в `src/lib/org/crypto.ts` (чистые функции над WebCrypto) — юнит-тестируется без БД и браузера через `node:crypto.webcrypto`. Версия схемы (`kdfParams`) хранится с каждой обёрткой, чтобы поднять итерации PBKDF2 без миграции всех записей.

### 5.3. Что придётся починить в существующем коде

Обезличивание сотрудников бессмысленно, если ПДн текут через побочные каналы. Ревизия:

| Место | Проблема | Что делаем |
|---|---|---|
| `Device.lastIp`, `Device.lastCity` | IP + геолокация — ПДн | хранить `ipHash` (HMAC с серверной солью) вместо IP; город округлять до страны или убрать; retention 90 дней |
| `LoginAttempt.email`, `.ip` | связка «кто откуда входил» | хранить хеш идентификатора и хеш IP; авточистка старше 30 дней (cron) |
| `Event.meta` | свободный JSON — может утечь что угодно | zod-схема на запись события, whitelist ключей; юнит-тест «в meta нет строк, похожих на e-mail/телефон» |
| `Note`, `AiMessage`, `SimulationRun.dialog` | сам ученик может написать «звонил Иванову И. И., +375...» | предупреждение в UI + кнопка «удалить всё» у ученика; в договоре — это данные, вносимые клиентом. Остаточный риск, полностью не устраняется |
| `Lead.name/contact` | публичная форма заявки — настоящие ПДн | не B2B-контур, но retention: удалять `DECLINED`-заявки через 6 месяцев |
| pino-логи | правило 9 «ПДн не логировать» | редактор-сериализатор: маскировать поля `email/phone/name/ip` на уровне логгера, а не на каждом вызове |
| Бэкапы | шифрование обязательно | проверить `docs/MIGRATION.md`, что фактически включено |
| GA4/Метрика | правило D-002 | подтвердить, что счётчики не подключаются в `(org)` и `(student)` — только `(marketing)` |

### 5.4. Что даёт обезличивание бизнесу

Не только снижение риска: **это аргумент в продаже.** Крупному клиенту (банк, фарма, госкомпания) проще согласовать закупку у поставщика, которому не нужно передавать данные сотрудников — отпадает поручение на обработку, споры со службой безопасности, отдельные согласия. Стоит вынести это на лендинг отдельным блоком (§8).

## 7. Обязательные e2e-тесты (по `CLAUDE.md`)

- Org-админ **не видит** сотрудников чужой организации — ни в UI, ни подстановкой id в Server Action.
- Сотрудник не может открыть `/org/*`.
- Самозапись по коду: код одноразовый, повторное использование отклоняется; при исчерпании мест лицензии — отказ с внятной ошибкой.
- Заморозка организации / истечение лицензии → урок и `playlist/key/сегмент` недоступны (проверка идёт через существующий `lib/access.ts`).
- Отзыв места у сотрудника освобождает место в пуле.
- Анонимная B2B-учётка создаётся без e-mail и имени; попытка передать `name/email/phone` в действие создания сотрудника отклоняется zod-схемой (а не просто скрыта в UI).
- Сотрудник занимает по одному месту в каждой из лицензий на курсы, которые ему открыли; отзыв освобождает место именно в этом пуле.
- Unit: подсчёт свободных мест, агрегаты отчёта, генерация логинов (`acme-0042`, без коллизий при параллельной активации кодов).
- Unit L2 (`lib/org/crypto.ts`): цикл «сгенерировать `orgKey` → обернуть фразой → развернуть» на `node:crypto.webcrypto`; неверная фраза даёт ошибку аутентификации AES-GCM, а не мусор; recovery-код разворачивает тот же `orgKey`; смена фразы перевыпускает обёртку, не трогая `labelEnc`.
- Тест-инвариант: ни один Server Action и ни один API-ответ не возвращает `labelEnc` в расшифрованном виде и не принимает `orgKey`/парольную фразу на сервер (грепом по сигнатурам + ревью-чеклист).

### Экраны

Владелец открывает кабинет клиента по тому же маршруту `/org/[orgId]` — второго интерфейса не существует, поэтому расхождений «у меня работает, у клиента нет» быть не может.

### L2-шифрование подписей (фаза 2.5)

`src/lib/org/crypto.ts` — WebCrypto без React и DOM, поэтому тестируется на настоящем
`node:crypto` (16 тестов): случайный ключ организации AES-256-GCM, обёртки под
парольную фразу (PBKDF2-SHA256, 600 000 итераций) и под recovery-код, шифрование
подписей.

Ключ существует **только в памяти вкладки** — ни localStorage, ни cookie: закрыли
вкладку, нужна фраза заново. На сервер уходят лишь blob и параметры KDF
(`setupOrgKeyAction` / `saveOrgKeyWrapAction` принимают строки и число итераций —
ни ключа, ни фразы там нет по конструкции схемы).

Кабинет полностью работает и без ключа: сотрудники видны по кодам, подписи —
удобство. Recovery-обёртка одна на организацию (unique-индекс с NULL в Postgres
не работает, поэтому прежняя удаляется явно). Неверная фраза даёт ошибку
аутентификации AES-GCM, а не «мусорный ключ», — отдельная проверка фразы не нужна.

**Секрет — четырёхзначный ПИН-код, а термин в интерфейсе — «имя»** (решение
владельца, 2026-08-21). Раньше это была парольная фраза от 10 символов, и её
просто не заводили: длинный секрет ради удобной таблицы никто держать в голове
не хочет. Цена решения зафиксирована в `validatePin`: четыре знака — 10 000
вариантов, и обладатель выгрузки `OrgKeyWrap` переберёт их офлайн, сколько
итераций PBKDF2 ни ставь. Поэтому формулировки в кабинете и в этом документе —
«мы имена не читаем, открытым текстом они нигде не лежат», а не «прочитать
невозможно». Онлайн-перебора нет: обёртка отдаётся только своему же
ответственному. Клиенту, которому нужна прежняя стойкость, ничто не мешает
ввести длинный код — минимум не запрещает большего.

**Забытый ПИН лечится сбросом, а не подсказкой.** `resetOrgKeyAction` (только
OWNER) удаляет обёртки ключа и обнуляет `labelEnc`: без ключа это всё равно
нечитаемый мусор, а без сброса клиент оказывается в тупике — старые имена не
показать, новые не завести (`setupOrgKeyAction` отказывает, пока обёртки есть).
Владелец при этом имён не получает: операция их уничтожает, а не открывает.
Доступы, прогресс и коды сброс не трогает.

**Удаление организации уносит и обезличенные учётки.** Каскада схемы мало:
`Enrollment.licenseId` обнуляется (SetNull), то есть доступ пережил бы удаление
организации. `deleteOrgAction` снимает доступы явно, удаляет учётки работников
и требует набрать наименование организации, если она не пуста. Исключение —
работники с сертификатом или заказом: `Certificate.userId` и `Order.userId`
держат пользователя без каскада, а проверка сертификата на `/verify` обязана
работать и после ухода клиента, поэтому такие учётки остаются заблокированными,
и их число возвращается вызывающему.

**Владелец платформы имён не видит и завести ключ не может** (решение
владельца, 2026-08-21). В кабинете клиента ему показывается плашка «работники
показаны кодами — и вам, и нам», обёртки ключа в его браузер не отдаются вовсе
(`layout.tsx`), а `setupOrgKeyAction`, `saveOrgKeyWrapAction` и
`setMemberLabelAction` отклоняют вызов от OWNER (`assertNotOwnerView`) — `auth:
"orgAdmin"` его пропускает, поэтому проверка нужна в самом действии. Причина не
техническая, а юридическая: как только платформа способна прочитать, кто стоит
за кодом, она становится оператором персональных данных работников — ровно то,
чего оферта `/offer-b2b` (п. 10) не предполагает. Побочная выгода — владельцу
не нужно помнить ещё один секрет: ПИН-код знает один человек у клиента.

### Отчёты и выгрузка (фаза 3)

`/org/[orgId]/reports`: разрезы по курсам (учатся / прошли / не начинали / средний
прогресс / балл / сертификаты), по подразделениям и по сотрудникам.

**XLSX собирается в браузере** (`lib/org/xlsx-client.ts`), а не на сервере, как
экспорт админ-аналитики. Причина принципиальная: подписи зашифрованы ключом, которого
у сервера нет, — собирали бы файл на сервере, пришлось бы отправить туда расшифрованные
ФИО и выбросить всю схему обезличивания. ExcelJS (≈900 КБ) грузится динамически по
клику, поэтому страница остаётся лёгкой. Без введённой фразы отчёт выгружается по
кодам — это рабочий сценарий; отдельный лист «О данных» фиксирует, включены подписи
или нет.
