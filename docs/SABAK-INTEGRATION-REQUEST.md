# Задача для SABAK: сервисный доступ для study.activesales

> Файл писался в проекте ACTIVE SALES (`salesup`) и предназначен для переноса в
> репозиторий SABAK как задание Claude Code. Ответная сторона интеграции описана
> в `docs/LIVE-SESSIONS-PLAN.md` проекта ACTIVE SALES.
> Дата: 2026-08-21.

## 0. Контекст в двух абзацах

ACTIVE SALES (`study.activesales.by/.kz/.ru/.uz`) — платформа онлайн-курсов по
продажам. В корпоративном тарифе продаётся пакет с живым тренером: вводная
онлайн-сессия (1 ч), итоговая онлайн-сессия (1 ч) и сопровождение группы. Встречи
хочется проводить на SABAK, но планировать и входить в них — из кабинета ACTIVE
SALES, не отправляя человека в другой сервис.

Тренер один — Виталий Дубовик. Слушатели — работники компании-клиента. **Их
персональных данных у ACTIVE SALES нет и не должно появиться**: работник входит
под обезличенным логином вида `acme-0042` (правило минимизации ПДн, Закон РБ
№ 99-З). Это ключевое ограничение всей интеграции: ни ФИО, ни e-mail, ни телефон
слушателя SABAK от нас не получит.

Изучение кода SABAK показало: функционально всё уже есть — standalone-встречи
(`POST /my/lessons`), гостевой вход без регистрации (`POST /m/:id/join`), режим
вебинара, записи с `RecordingShare`, посещаемость через вебхуки LiveKit,
брендирование лобби. **Не хватает только машинного (server-to-server) доступа**:
сегодня любая операция требует JWT живого пользователя, полученного по паролю.
Об этом и задача.

## Задача 0 (без кода): подготовить аккаунт

Выполняется руками SYSTEM_ADMIN'ом SABAK, до и независимо от разработки.

1. **Workspace** режима `BUSINESS` (`School.mode = BUSINESS`) с названием
   «ACTIVE SALES» и брендированием:
   - `brandLogoUrl` = `https://study.activesales.by/logo.png` (513×513, PNG с
     прозрачностью);
   - `brandColor` = `#f4003a`.
2. **Учётка тренера** — роль `TEACHER`, `workspaceMode: BUSINESS`, статус ACTIVE.
   Создаётся через `POST /api/v1/admin/users` (schema `CreateUserSchema`) или
   админку:
   ```json
   {
     "email": "dubovik.vitaliy@gmail.com",
     "firstName": "Виталий",
     "lastName": "Дубовик",
     "role": "TEACHER",
     "workspaceMode": "BUSINESS",
     "password": "<сгенерировать, передать владельцу ACTIVE SALES отдельно>"
   }
   ```
   > Владелец прислал адрес как `dubovik.vitaliy@gmail.co` — почти наверняка
   > опечатка в домене. Перед созданием подтвердить: `.com` или всё же `.co`.
3. **Тариф/entitlements** этой учётки должны включать как минимум
   `FEATURES.CREATE_LESSON`, `FEATURES.CREATE_MEETING` и запись встреч —
   иначе интеграция упрётся в 403 на первой же продаже.
4. **Срок хранения записей** для workspace: `recordingRetentionDays` выставить
   явно (предложение — 180 дней) и сообщить значение — ACTIVE SALES пропишет его
   в оферту для организаций.

Итог этапа: тренер может войти в SABAK и создать встречу руками. Этого уже
достаточно, чтобы ACTIVE SALES запустил ручной режим, пока идёт разработка.

## Задача 1: сервисные API-ключи (S2S)

**Проблема.** Сейчас единственный способ для внешнего сервиса — хранить логин и
пароль тренера и логиниться его же ручкой. Это плохо: пароль живёт в чужом
сервисе, ротация ломает интеграцию, скоупов нет, отозвать доступ можно только
сменой пароля (и тогда отвалится сам тренер).

**Что реализовать.**

1. Модель `ApiClient`:
   ```prisma
   model ApiClient {
     id          String    @id @default(uuid())
     name        String              // "ACTIVE SALES"
     clientId    String    @unique
     secretHash  String              // argon2id/bcrypt от client_secret
     schoolId    String              // tenant, в котором работает ключ
     actAsUserId String              // от чьего имени действует (учётка тренера)
     scopes      String[]            // см. ниже
     lastUsedAt  DateTime?
     revokedAt   DateTime?
     createdAt   DateTime  @default(now())
   }
   ```
2. Эндпоинт `POST /api/v1/oauth/token` с `grant_type=client_credentials`:
   - вход: `client_id`, `client_secret` (Basic или в теле);
   - выход: `{ access_token, token_type: "Bearer", expires_in }` — короткий JWT
     (15–30 мин), в payload `sub = actAsUserId`, `schoolId`, `scopes`, `cid`;
   - rate-limit как у `/auth/local/login`, неверный секрет — 401 без подсказок.
3. Скоупы (минимально необходимые, без «полного доступа»):
   - `lessons:write` — создать/изменить/отменить встречу;
   - `lessons:read` — карточка встречи, статус, посещаемость;
   - `guests:issue` — выдать гостевой доступ участнику;
   - `recordings:read` — список записей и выдача ссылки.
   Всё остальное (журнал, оценки, чужие уроки, админка) ключу недоступно —
   guard обязан отказывать по scope, а не только по роли.
4. Управление ключами — в админке SYSTEM_ADMIN: создать (секрет показывается
   один раз), отозвать, посмотреть `lastUsedAt`. Каждое действие ключа пишется в
   `AdminAuditLog` с `clientId`.
5. Тесты: выдача токена, отказ по неверному секрету, отказ по отозванному ключу,
   отказ при нехватке scope, tenant-изоляция (ключ одного workspace не видит
   уроки другого).

## Задача 2: чего не хватает в API поверх существующего

Все эндпоинты — под Bearer-токеном из задачи 1.

### 2.1 Создание встречи

Существующий `POST /my/lessons` подходит, но нужен приём внешнего ключа
идемпотентности и явного часового пояса:

```http
POST /api/v1/my/lessons
Idempotency-Key: <uuid внешней системы>

{
  "title": "Вводная сессия — отдел продаж «Ромашка»",
  "scheduledAt": "2026-09-10T07:00:00Z",   // всегда UTC
  "durationMinutes": 60,
  "kind": "WEBINAR",                        // или MEETING для итоговой
  "allowGuests": true,
  "guestRequireFullName": false,            // анкету гостя НЕ включать
  "guestRequirePosition": false,
  "guestRequireContact": false,
  "eduGroupName": "Ромашка — отдел продаж"  // создать группу, если её нет
}
```

Ответ: `{ id, livekitRoomName, guestUrl, status, scheduledAt }`, где `guestUrl` —
готовая ссылка `https://<sabak>/m/<lessonId>`.

Требование: повтор запроса с тем же `Idempotency-Key` возвращает ту же встречу,
а не создаёт вторую. Сеть между сервисами ненадёжна, а дубль встречи в календаре
тренера — это его сорванный день.

Дополнительно нужны: `PATCH /my/lessons/:id` (перенос времени) и
`DELETE /my/lessons/:id` (отмена) с теми же правами.

### 2.2 Гостевой доступ по внешнему идентификатору

Сейчас `POST /m/:lessonId/join` публичный и заводит гостя по введённому имени.
Для нас нужен серверный вариант: ACTIVE SALES уже проверил, что этот работник
имеет право на встречу, и просит доступ **от его имени**:

```http
POST /api/v1/lessons/:lessonId/guest-access
{ "externalId": "acme-0042", "displayName": "acme-0042" }
```

Ответ: `{ joinUrl, joinToken, expiresAt }` — одноразовая ссылка/токен со сроком
жизни порядка 15 минут, при переходе по которой человек попадает в лобби уже
авторизованным.

Требования:
- `externalId` — непрозрачная строка ≤ 64 символов; SABAK **не должен** пытаться
  разобрать её как ФИО, e-mail или телефон и не обязан её никуда показывать,
  кроме списка участников;
- повторный вызов с тем же `externalId` возвращает того же гостя (стабильный
  идентификатор нужен для отметки присутствия);
- поля `email`, `fullName`, `phone` в этом эндпоинте не принимаются вовсе —
  это защита от того, чтобы ПДн случайно приехали при доработках UI.

### 2.3 Посещаемость сводкой

```http
GET /api/v1/lessons/:lessonId/attendance/summary
```

Ответ:
```json
{
  "lessonId": "...",
  "finishedAt": "2026-09-10T08:02:11Z",
  "participants": [
    { "externalId": "acme-0042", "attended": true },
    { "externalId": "acme-0043", "attended": false }
  ]
}
```

`attended` считается по порогу присутствия (по умолчанию 10 минут, параметр
`?minMinutes=`). Поминутный хронометраж нам не нужен и лучше, чтобы он и не
передавался: владелец ACTIVE SALES сознательно ограничил отчёт компании фактом
«был / не был».

### 2.4 Ссылка на запись по требованию

Постоянных ссылок на записи ACTIVE SALES не хранит: запись принадлежит только
той компании, для которой прошла встреча, и раздаётся из её кабинета после
проверки прав.

```http
GET  /api/v1/lessons/:lessonId/recordings          # список: id, готовность, длительность
POST /api/v1/recordings/:recordingId/link          # { "ttlMinutes": 60 } → { url, expiresAt }
```

Требования: `allowDownload: false` по умолчанию, TTL ≤ 24 ч, каждый вызов —
строка в `RecordingShareAccess` (кто из клиентов запросил и когда). Реализуемо
поверх существующего `RecordingShare` — нужен только программный вход.

### 2.5 Вебхуки в обратную сторону

ACTIVE SALES не должен опрашивать SABAK по таймеру. Нужны исходящие вебхуки на
URL, заданный при создании `ApiClient`:

| Событие | Когда | Payload |
|---|---|---|
| `lesson.started` | тренер начал встречу | `lessonId`, `startedAt` |
| `lesson.finished` | встреча завершена | `lessonId`, `endedAt` |
| `recording.ready` | Egress выгрузил файл | `lessonId`, `recordingId`, `durationSeconds` |
| `attendance.ready` | посещаемость посчитана | `lessonId`, `participants[]` (как в 2.3) |

Подпись — HMAC-SHA256 от тела в заголовке `X-Sabak-Signature` с секретом
клиента, плюс `X-Sabak-Timestamp` (защита от повтора, окно 5 минут). Ретраи с
экспоненциальной паузой, не менее 5 попыток. Доставка «хотя бы один раз» —
принимающая сторона идемпотентна.

## Задача 3: что менять НЕ нужно

Чтобы не потратить время впустую:

- **CSP и `frame-ancestors` трогать не надо.** ACTIVE SALES не встраивает
  страницы SABAK в iframe: на первом этапе это ссылка в новой вкладке, на
  втором — собственная комната на `@livekit/components-react` с токеном,
  полученным по API. Ослаблять защиту от кликджекинга ради нас не требуется.
- **CORS тоже не нужен.** С API SABAK разговаривает только сервер ACTIVE SALES,
  браузер пользователя — нет. Единственное браузерное соединение — WebSocket к
  LiveKit SFU по токену.
- **Kundelik-контур не затрагивается.** Мы живём в standalone/BUSINESS-ветке:
  ни расписания из Kundelik, ни оценок, ни журнала.

## Приёмка

Сценарий, который должен пройти целиком на стенде:

1. По `client_id`/`client_secret` получен токен, в нём есть только четыре скоупа.
2. `POST /my/lessons` с `Idempotency-Key` создал вебинар на завтра; повторный
   запрос с тем же ключом вернул ту же встречу (в БД одна запись).
3. `POST /lessons/:id/guest-access` с `externalId: "acme-0042"` вернул ссылку;
   переход по ней открывает лобби без анкеты; в списке участников — `acme-0042`.
4. Тренер начал встречу → прилетел `lesson.started` с валидной подписью.
5. После завершения пришли `lesson.finished`, `recording.ready` и
   `attendance.ready`; в последнем — только `externalId` и `attended`.
6. `POST /recordings/:id/link` вернул ссылку на час, скачивание запрещено, факт
   выдачи виден в `RecordingShareAccess`.
7. Ключ отозван → все запросы отвечают 401, тренер при этом продолжает работать.
8. Ключ workspace A не видит и не создаёт ничего в workspace B.

## Ожидаемый объём

Задачи 1 и 2 — это примерно одна модель, один guard, один контроллер токенов,
четыре-пять тонких эндпоинтов поверх существующих сервисов и один воркер
вебхуков. Вся тяжёлая часть (LiveKit, Egress, гости, записи, посещаемость) в
SABAK уже написана — мы просим только программный вход к ней.
